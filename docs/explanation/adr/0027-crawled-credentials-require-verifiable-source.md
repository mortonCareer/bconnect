# ADR-0027: 크롤링 자격·인증은 검증 가능한 출처만 저장한다

- **Status**: Accepted
- **Date**: 2026-07-23
- **Deciders**: @manamana32321
- **Related**: [#1019](https://github.com/mortonCareer/bconnect/issues/1019), [packages/business](https://github.com/mortonCareer/bconnect/tree/dev/packages/business)

## Context

`crawled_credentials` 테이블·엔티티·리포지토리는 처음부터 존재했지만, 크롤러가 여기에 행을 넣는 코드가 없어 실제 저장은 계속 0건이었다. #1019에서 이 누락을 고치려다 더 근본적인 질문이 나왔다 — **누가 이 데이터를 공급하는가.**

결정 시점의 상태:

- 이 테이블의 유일한 공급원은 기술자 노션 검수 DB의 "인증" 항목이었다. 사람이 손으로 입력한 값을 `_review_page_to_member`가 실어 왔다.
- 그 노션 DB는 폐기됐다. 현행 수집 경로는 `dry-run JSON → --export-db → 서비스 DB` 직행이다.
- 블로그 크롤링 자체는 자격·인증을 수집하지 않는다.

즉 저장 코드를 고쳐도 채울 데이터가 없다. 그래서 "어디서 가져올 것인가"를 정해야 했고, 이 데이터가 사용자에게 **업체 신뢰도 판단 근거**로 노출된다는 점이 결정을 좌우하는 force였다.

## Options

### Option 1: LLM이 블로그 글에서 자격·인증을 추출

이미 시공분야·경력·지역을 뽑는 LLM 분류가 돌고 있으므로, 응답 형식에 항목을 추가하는 정도로 구현된다.

- **장점**: 추가 비용이 사실상 없다(호출·입력 텍스트 동일). 수집 텍스트 614건 중 **37%가 면허·자격증·수상 등을 언급**한다.
- **단점**: 언급과 보유가 구분되지 않는다. 실측 문구 예시:
  - `"토공사, 석면해체공사면허를 갖고있는 법인회사입니다"` — 보유 주장
  - `"건설면허를 빠르게 등록하기 위해"` — 면허 등록 **대행 광고**
  - `"천안미용학원 피부국가자격증 취득 과정"` — 업종 무관, 타인 이야기
  - `"* 사업자등록증 또는 폐업사실증명원"` — 단순 서류 안내 문구
- **단점**: 근본적으로 **자칭(self-claim)** 이다. 원 출처가 업체의 홍보글이므로 아무리 분류가 정확해도 "그렇게 주장했다"까지만 참이다.

### Option 2: 공공기관 데이터와 대조해 검증된 것만 저장

[`packages/business`](https://github.com/mortonCareer/bconnect/tree/dev/packages/business)가 이미 사업자등록번호로 국토교통부(KISCON)·한국전기공사협회·한국소방시설협회·국세청을 조회한다. career 원클릭 기능이 이 경로를 쓴다.

- **장점**: 발급기관이 출처이므로 **검증된 사실**이다. 업종명·등록번호·등록일·대표자까지 확보된다.
- **단점**: 커버리지가 낮다. 실측:

  | 단계                       | 건수                |
  | -------------------------- | ------------------- |
  | 수집된 업체                | 614                 |
  | 사업자등록번호 보유        | 187 (30%)           |
  | 10자리 정상형              | 180                 |
  | `kiscon_registration` 매칭 | **9 (전체의 1.5%)** |

  KISCON은 건설업 등록업체 명부이고 우리 수집 대상은 대부분 개인 기술자·소규모 시공팀이라 모집단이 겹치지 않는다.

- **단점**: 크롤링 데이터(dev DB)와 KISCON 데이터(prod DB)가 서로 다른 데이터베이스에 있어 조인이 불가능하다. 어느 쪽으로든 옮기는 작업이 선행된다.

### Option 3: 저장 경로만 유지하고 채우지 않는다

`crawled_credentials`에 INSERT하는 코드는 넣되, 공급원이 없으므로 실제 저장은 0건으로 둔다.

- **장점**: 스키마가 늘지 않는다(테이블은 이미 존재). 공급원이 생기면 즉시 동작한다.
- **장점**: 검증되지 않은 자격 정보가 사용자에게 노출되지 않는다.
- **단점**: 당분간 빈 테이블이다. 사정을 모르는 사람이 "왜 안 채우지"라고 다시 물을 수 있다(이 ADR이 그 답이다).

## Decision

**Option 3을 선택한다. 자격·인증은 발급기관이 확인해 준 것만 저장한다.**

우선한 force는 **정확성**이다. 자격·인증은 사용자가 업체를 고르는 직접 근거이고, 틀렸을 때의 손해가 크다. 블로그 홍보글에서 뽑은 자칭을 자격 데이터로 저장하면, 데이터 자체보다 **"우리가 보여주는 인증 정보"라는 표시의 신뢰**가 먼저 깨진다.

받아들인 트레이드오프: 커버리지를 포기했다. Option 1이면 37%를 채울 수 있었지만, 그 37%는 검증되지 않은 주장이다. 빈 칸이 틀린 값보다 낫다고 판단했다.

Option 2는 방향이 옳지만 지금 커버리지(1.5%)와 DB 분리 문제 때문에 별도 작업으로 미룬다. 폐기가 아니라 **보류**다.

이 결정은 다음 원칙으로 일반화된다 — **크롤링 데이터는 자칭과 검증된 사실을 구분한다.** 시공분야·경력·지역처럼 틀려도 필터가 조금 부정확해지는 값은 자칭이라도 저장하지만, 자격·인증처럼 신뢰를 직접 표상하는 값은 검증된 출처만 인정한다.

## Consequences

- **좋은 결과**: 검증되지 않은 자격 정보가 화면에 노출될 위험이 없다. 실회원의 자격(본인 증빙 업로드 또는 공공기관 원클릭 조회)과 신뢰 수준이 뒤섞이지 않는다.
- **좋은 결과**: `crawled_credentials` 저장 경로가 복구돼, 공급원이 생기는 시점에 코드 수정 없이 바로 채워진다.
- **나쁜 결과**: 크롤링 업체 상세 화면에 자격·인증이 계속 비어 있다. 실회원 대비 정보량이 적어 보인다.
- **중립적 결과**: 블로그 텍스트에 담긴 자격 언급 37%는 `about`·`content`에 원문 그대로 남아 있다. 나중에 방침이 바뀌면 재크롤 없이 다시 판단할 수 있다.

## Notes

- 후속 검토 대상: 크롤링 업체를 `packages/business` 경로로 검증하는 작업. 선행 과제는 (1) 크롤링 데이터와 KISCON 데이터의 DB 분리 해소, (2) 커버리지 1.5%가 서비스 가치를 만드는지 판단.
- KISCON 매칭 9건은 "건설업 등록을 갖춘 업체"라는 차별화 정보이기도 하다. 자격 데이터가 아니라 업체 등급·신뢰 표시로 쓰는 방향은 기획 판단 영역이다.
- 노션 검수 DB 폐기로 `apps/crawler/src/crawler/notion.py`는 현행 경로가 아니다. 이 파일을 근거로 데이터 공급원을 추론하지 말 것.
