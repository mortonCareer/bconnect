# ADR-0027: 역할 기반 라우트 게이팅은 클라이언트 게이트 컴포넌트로 한다

- **Status**: Accepted
- **Date**: 2026-07-29
- **Deciders**: @manamana32321
- **Related**: [#1099](https://github.com/mortonCareer/bconnect/issues/1099), [#1066](https://github.com/mortonCareer/bconnect/issues/1066), [PR#1083](https://github.com/mortonCareer/bconnect/pull/1083), [스펙](../../reference/specs/2026-07-29-fe-role-route-gating.md)

## Context

BE 가 회원 역할에 `CAREER`, `PLAN` 을 추가했습니다. 역할은 온보딩 완료 표식이며 ([ProfileService](../../../apps/api/src/main/java/to/bconnect/api/core/domain/profile/ProfileService.java), [CompanyService](../../../apps/api/src/main/java/to/bconnect/api/core/domain/company/CompanyService.java)), [SecurityConfig](../../../apps/api/src/main/java/to/bconnect/api/security/SecurityConfig.java) 가 이 역할로 엔드포인트를 막습니다. FE 가 역할을 보지 않아, 프로필 없는 회원이 career 에 들어가면 화면은 열리는데 주요 동작이 전부 403 이 됩니다.

판정을 어디서 할지가 이 결정의 핵심인데, 다음 제약이 선택지를 크게 줄입니다.

- access token 은 브라우저 JS 메모리에만 있습니다 ([client.ts](../../../packages/api-client/src/client.ts)). 쿠키도 localStorage 도 아닙니다
- refresh token 쿠키는 경로가 `/api/v1/auth` 로 좁혀져 있어 페이지 요청에 실리지 않습니다 ([CookieProvider](../../../apps/api/src/main/java/to/bconnect/api/security/jwt/CookieProvider.java))
- 따라서 **Next 서버는 회원의 로그인 상태도 역할도 알 수 없습니다**
- 실제 권한 강제는 BE 가 합니다. FE 게이팅은 잘못된 화면을 보여주지 않기 위한 것입니다
- career 는 홈 피드와 타인 프로필이 공개인데, 같은 레이아웃 아래에 보호 페이지가 섞여 있습니다

## Options

### Option 1: 표시 쿠키에 역할을 함께 담고 proxy 에서 판정

로그인·토큰 갱신 시 토큰의 역할 정보를 읽어 `bc_auth_hint` 쿠키에 같이 적고, `proxy.ts` 가 그 값을 보고 서버에서 이동시킵니다.

- **장점**: 서버 이동이라 보호 페이지가 한 프레임도 그려지지 않습니다. 페이지 코드를 아예 내려받지 않습니다
- **단점**: 역할이라는 같은 정보가 두 곳에 존재합니다. 쿠키 형식 변경, 기존 쿠키 호환 처리, 어긋났을 때 스스로 회복하는 장치가 모두 필요합니다
- **단점**: 배포 시점에 이미 로그인해 있던 회원은 역할 정보가 없는 쿠키를 들고 있어, 자칫 전원이 생성 페이지로 튕깁니다

### Option 2: 클라이언트 게이트 컴포넌트

`useGetMyMember().roles` 를 읽어 역할이 없으면 생성 페이지로 이동시키는 컴포넌트를 레이아웃에 둡니다.

- **장점**: 역할의 출처가 서버 하나입니다. 복사본이 없으니 어긋날 일이 없습니다
- **장점**: `/members/me` 는 DB 를 직접 읽으므로 토큰에 담긴 값보다 최신입니다
- **단점**: 판정에 왕복이 필요해, 새로고침 직후에는 잠시 판정할 수 없는 구간이 생깁니다

### Option 3: 서버 컴포넌트나 데이터 접근 계층에서 검증

Next 공식 문서가 1순위로 권하는 방식입니다.

- **단점**: 성립하지 않습니다. 서버가 토큰을 볼 수 없습니다

### Option 4: 폴더 구조로 공개·보호를 분리

라우트 그룹을 `(public)` 과 `(protected)` 로 나눕니다.

- **단점**: `/profile/{id}` 는 공개인데 `/profile/edit` 는 보호라 경로가 겹칩니다
- **단점**: 역할 조합이 늘면 그룹 수가 곱으로 늘어납니다

### Option 5: 권한 라이브러리(CASL 등) 도입

- **단점**: 지금 필요한 것은 역할 목록에 포함되는지 확인하는 일뿐입니다. 규칙 엔진을 들일 이득이 없습니다

## Decision

**Option 2 를 택합니다.**

Option 3·4 는 우리 구조에서 성립하지 않으므로 실질 선택지는 1 과 2 입니다. 둘의 차이는 **정보를 복사할 것인가**로 좁혀집니다.

Option 1 이 얻는 것은 "보호 화면이 한 프레임도 안 보이는 것" 인데, 이 상황을 겪는 사람은 온보딩을 마치지 않은 회원뿐이고 그것도 가입 직후 한 번입니다. 반면 복사에 따르는 비용(형식 변경, 호환 처리, 회복 장치, 갱신 지점 관리)은 코드에 영구히 남습니다. 이득이 일회성이고 비용이 영구적이라 Option 2 를 택했습니다.

판정할 수 없는 구간에서는 본문 자리에만 스켈레톤을 보여줍니다. 하단 네비게이션과 사이드바는 게이트 바깥에 두어 그대로 유지합니다. 이 구간은 브라우저 새로고침에서만 나타나며, 앱 안에서 페이지를 옮길 때는 캐시가 살아 있어 보이지 않습니다.

조회가 실패하면 막지 않고 통과시킵니다. 네트워크 문제를 "권한 없음" 으로 잘못 판정하지 않기 위해서입니다.

기존 `proxy.ts` 의 로그인 가드는 유지합니다. 로그인 여부는 쿠키만 보면 되어 왕복이 필요 없고, 서버에서 막으면 페이지 코드를 내려받지 않아도 됩니다. 두 가드는 중복이 아니라 서로 다른 질문을 맡습니다.

## Consequences

- **좋은 결과**: 역할 정보가 서버 한 곳에만 있어 동기화 코드가 필요 없습니다
- **좋은 결과**: 새 보호 페이지는 아무 작업 없이 자동으로 보호됩니다. 공개 페이지만 목록에 등록하면 됩니다
- **좋은 결과**: career 와 plan 이 같은 컴포넌트를 씁니다. 정책이 갈라질 자리가 없습니다
- **나쁜 결과**: 브라우저를 새로고침하면 본문 자리에 잠시 스켈레톤이 보입니다
- **나쁜 결과**: 이것은 보안 경계가 아닙니다. 브라우저에서 우회하면 화면은 열립니다. 실제 차단은 BE 가 합니다
- **중립적 결과**: 화면 요소 하나를 숨기는 용도로는 쓸 수 없습니다. 그 경우 참/거짓을 답하는 훅이 따로 필요하며, 쓰이는 곳이 생기면 그때 만듭니다

## Notes

다시 볼 시점:

- 역할 외에 조건이 붙는 권한(본인 글만 수정, 프로젝트 참여자만 등)이 FE 에 필요해지면 권한 라이브러리를 다시 검토합니다
- 오프라인 지원이 요구사항이 되면 캐시 저장을 검토합니다. 다만 그때는 로그아웃 시 캐시 파기가 의무가 됩니다
- 인증 구조가 바뀌어 서버가 세션을 볼 수 있게 되면 Option 3 이 1순위로 돌아옵니다

비회원에게 로그인을 권하는 [`useLoginGate()`](<../../../apps/plan/src/app/(main)/_components/LoginGateProvider.tsx>) 와는 축이 다릅니다. 진입 차단은 이 ADR 의 게이트가, 동작 시도 시 유도는 `useLoginGate` 가 맡습니다.
