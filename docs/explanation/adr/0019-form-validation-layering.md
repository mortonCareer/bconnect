# ADR-0019: 폼 검증 계층 분리

- 상태: 승인됨
- 날짜: 2026-06-06
- 담당자: @manamana32321, @fine-pine

## 개요

양식 제출 시 입력 검증을 어느 계층에서, 얼마나 엄격하게 할지가 정해져 있지 않다.

- BE는 Java, FE는 TypeScript로 언어가 다르다 → zod 검증 스키마를 공유할 수 없다. 검증 규칙은 어느 방식을 택하든 양쪽에 따로 존재하게 된다.
- [ADR-0013](./0013-form-handling-standard.md)은 FE 폼을 RHF+zodResolver로 짜고 에러를 어떻게 *표시*할지 정했다. 그러나 FE/BE 검증 *경계*는 다루지 않았다. 경계란 누가 무엇을 얼마나 막는지를 뜻한다.

## 선택지

### 옵션 1: FE만 검증

단점

- 클라이언트 우회 시 무방비. 보안·데이터 무결성 구멍. 탈락.

### 옵션 2: BE만 검증

단점

- 모든 입력 오류가 서버 왕복 후에야 드러난다. 즉각 피드백 없음 → UX 나쁨. 탈락.

### 옵션 3: 양 계층 + 단일 스키마 공유(SSOT)

단점

- 언어가 달라 스키마를 한 곳에서 정의해 양쪽에 흘리는 메커니즘 비용이 크다. [ADR-0015](./0015-be-code-as-api-ssot.md)에서 교차언어 SSOT 복잡도를 이미 기각한 결정과 충돌. 탈락.

### 옵션 4: 양 계층 + 독립 스키마, BE 허용범위 ⊇ FE 허용범위 (채택)

- FE는 UX용 엄격 검증, BE는 무결성용 느슨한 최후 방어선. 스키마는 각자 유지하되 방향 불변식을 건다.

## 결정사항

옵션 4 채택.

1. FE는 기본 검증을 맡는다. 목적은 UX다. zod 스키마로 제출 전 검증해 즉각 피드백을 주고 불필요한 서버 왕복을 없앤다. [ADR-0013](./0013-form-handling-standard.md)의 RHF+zodResolver 인프라 위에서 동작.
2. BE는 최후 방어선을 맡는다. 데이터 무결성·악용 방지·DB 제약만 강제한다. FE 검증 스키마보다 반드시 느슨해야 한다.
3. 불변식: FE가 통과시킨 입력은 BE도 통과시킨다. 즉 BE 허용집합 ⊇ FE 허용집합. 두 스키마는 언어가 달라 드리프트가 불가피하다. 가장 나쁜 실패는 *FE는 OK라는데 서버가 거부*하는 경우다.
4. FE 글자 수 상한은 2의 n승. BE의 요청사항이다.

## 기대 효과

- 좋은 결과: 클라이언트 우회는 BE 방어선이 막아 보안을 확보한다. 입력 오류는 FE가 즉시 잡아 UX를 확보한다. "FE는 통과했는데 서버가 거부" 실패를 불변식으로 구조적 제거.
- 나쁜 결과 / 비용: 검증 규칙이 두 언어에 중복 → 유지보수 부담·드리프트 가능. BE 최후 방어선 구체 규칙은 아직 미정. 후속 BE 결정에 의존한다.
- 중립: 공유 스키마 SSOT는 포기.

## 메모

후속:

- BE 최후 방어선 구체화
