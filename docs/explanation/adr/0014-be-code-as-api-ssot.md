# ADR-0014: BE 코드를 API 기준으로 (스펙 우선 개발 철회)

- **Status**: Accepted
- **Date**: 2026-05-28
- **Deciders**: @fine-pine @manamana32321
- **Related**: [ADR-0003](./0003-openapi-3-1-with-domain-split.md) (스펙 구조 결정 — 유지), [ADR-0006](./0006-dev-as-staging.md)

## Context

지금까지 우리 팀은 명시적 결정 없이 **OpenAPI 스펙(yaml)을 기준으로 BE/FE를 만드는 방식**으로 일해왔다:

- CTO가 스펙을 먼저 쓴다
- CEO는 스펙을 보고 BE를 구현한다
- FE는 스펙에서 자동 생성된 코드(orval)와 mock(MSW)를 보고 작업한다

이 방식을 운영하면서 다음 문제가 쌓였다.

### 1. BE 개발 사이클이 매우 복잡해진다

처음부터 완벽한 스펙 작성은 BE 입장에서 불가능에 가깝다. 구현 과정에서 결정되는 스펙이 많기에 필연적으로 후속 변경 사항이 생긴다. 이 변경 사항을 별도의 작업으로 처리하는데 드는 비용이 매우 크다.

### 2. 스펙 바꾸면 다른 사람 FE 작업까지 막힌다

스펙을 바꾸면 FE 쪽은 자동으로 새 코드가 생성된다. 그래서 기존 FE 호출부가 새 스펙과 안 맞게 되어 빌드가 깨진다. 이 상태에서 누가 무관한 FE 작업으로 PR을 올리면 그 PR의 CI도 같이 깨진다. **자기 변경이 아닌데 자기 PR이 막히는 상황**이 생긴다.

### 3. BE는 스펙과 안 맞아도 모른다

BE는 스펙에서 자동 생성하는 단계가 없다. 사람이 직접 컨트롤러/DTO를 작성한다. 그래서 스펙이 바뀌어도 BE 코드를 안 바꾸면 BE 빌드는 그냥 통과한다. 스펙과 BE가 다르다는 사실은 **사용자가 실제로 호출할 때**, 즉 운영 환경에서 발견된다.

### 4. 안 맞는 부분이 쌓일수록 정리 비용이 빠르게 늘어난다

문제 1처럼 안 맞는 호출부가 dev 브랜치에 쌓이면, dev → main 합칠 때 한 번에 다 고쳐야 한다. 1개 고치는 데 5분이면 30개는 반나절 이상 걸린다. 미룰수록 더 비싸진다.

### 5. 문제를 막으려면 한 PR에 다 묶어야 하는데, 협업 비용이 크다

위 문제를 모두 막는 방법은 스펙 + BE + FE를 한 PR에 같이 넣는 것이다. 그런데 BE는 CEO, FE는 CTO/FE 담당이라 한 PR에 묶으려면 두 사람이 같은 브랜치에서 협업해야 한다. 4명 팀에는 부담이 크다.

### 6. 스펙 우선 개발에 대한 팀 경험이 부족하다

위 문제를 도구로 막을 수는 있다(BE-스펙 일치 자동 검사, staging 환경에서 실제 호출 테스트 등). 그러나 그 도구들을 다 도입하고 안정화하는 데 드는 학습/운영 비용이 우리 팀에 크다.

## Options

### Option 1: 지금 방식 유지하면서 보완 도구 도입

- 스펙 그대로 두고, BE-스펙 자동 검사 + staging 자동 테스트 + 안 맞는 부분 자동 측정 + 한 PR 묶기 정책을 도입한다.
- **장점**: 스펙 단위 리뷰와 BE/FE 병렬 개발이라는 이득이 유지된다.
- **단점**: 도구 4개를 모두 안정시키는 비용이 큼, 경험 부족

### Option 2: BE 코드를 기준으로 돌아가기

- BE 컨트롤러/DTO가 기준이다. 스펙은 BE를 따라 만들어진다(자동 생성 또는 손으로 갱신).
- FE는 스펙에서 자동 생성한 코드와 MSW를 그대로 쓴다. 다만 스펙의 출처가 BE가 된다.
- **장점**: 문제 1, 2, 3이 자연스럽게 사라진다. BE가 기준이면 스펙이 BE와 어긋날 일이 없다. 팀에 익숙한 방식이다.
- **단점**: FE 작업이 BE 완료에 의존하게 된다(MSW로 일부 완화). 스펙 단위로 리뷰하던 흐름이 약해진다.

## Decision

**Option 2 (BE 코드 기준)** 채택.

이유:

- Option 1의 보완 도구들을 모두 안정시키기까지 드는 비용이, 현재 스펙 우선 개발이 주는 이득보다 크다고 판단했다.
- Option 2는 팀에 가장 익숙한 방식이고, 위 문제 1~3이 정의상 사라져 즉시 안정적으로 돌릴 수 있다.

## Consequences

- **좋은 점**:
  - 스펙 변경이 다른 사람 FE PR을 깨뜨리는 일이 없다.
  - BE와 스펙이 어긋나서 운영에서 터지는 일이 없다.
  - dev → main 합칠 때 쌓인 문제를 한 번에 푸는 부담이 없다.
  - 팀에 익숙한 방식이라 학습 비용이 없다.
- **나쁜 점**:
  - FE가 BE 완료를 기다려야 한다(MSW로 일부 완화).
  - 스펙 단위로 리뷰하던 흐름이 약해진다. API 설계 검토 시점이 BE 작성 시점으로 옮겨간다.
- **중립적**:
  - orval, MSW 도구는 그대로 쓴다. 스펙 yaml도 유지한다. 위치(기준)만 BE로 옮긴다.
  - 스펙 yaml을 어떻게 만들지(자동 생성 vs 손으로 갱신)는 별도 결정 — CEO가 정함.
