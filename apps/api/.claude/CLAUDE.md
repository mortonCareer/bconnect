# 가이드라인

## 제약
- `/docs` 문서를 SSOT로 간주합니다.
- 계획 문서를 작성하지 마세요.
- 모든 변경사항은 사용자에게 승인받아야 합니다.
- 사용자가 승인한 사항과 AI가 제안한 사항을 구분하세요.
- 프로젝트 내부 코드를 기반으로 코드 변경사항을 제안하세요.
- 라이브러리 사용시 공식 문서를 기반으로 코드를 작성하세요.
- 적절한 디자인 패턴을 활용하세요.
- 변경사항에 따른 레거시를 제거하세요.
- 대화 내역을 바탕으로 체크리스트를 관리하세요.
- 특정 명령어에 대한 오류가 3회 이상 발생한 경우 해당 작업을 건너뛰고, 보고하세요.

## 구현
- `클래스`-`인터페이스`-`구현` 순서로 계획을 논의하고 수행하세요.
- 계획을 종료할 때는 커밋 메시지를 제안하고 빌드 및 테스트를 수행하세요.
- 커밋 메시지는 Git 명령어를 사용하지 않고 대화 내역을 바탕으로 제안하세요.

## 테스트
- `통합 테스트`-`단위 테스트` 순서로 계획을 논의하고 수행하세요.
    - 통합 테스트 대상 : `controller`
    - 단위 테스트 대상 : `controller`, `service`
- 필요한 경우 `fixture`를 작성하세요.
- 객체와 매개변수에 대해 상태값, 경계값을 분석하세요.
- 분석된 결과와 에러코드를 포함한 모든 케이스를 정리하세요.
- 행위 검증 대신 상태 검증을 수행하세요.
- 테스트 커버리지 80%를 충족해야 합니다.

## 디버깅
- 버그 발생시 Console 및 에러 메시지를 확인하며 원인 파악을 위한 단계적 계획을 수립합니다.
- 버그 발생시 최소 재현 케이스를 작성하며 구체적인 원인을 파악합니다.
- 디버깅을 위한 변경사항을 사용자에게 제한하고 승인받으세요.
- 버그가 해결되었다면 커밋메시지와 함께 재발 방지 대책을 제안하세요.
